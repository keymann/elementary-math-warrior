# 수학 서바이버 클론 — 분석 및 작업 계획

> 대상: https://mathsurvivorbh.netlify.app/ (수달쌤, 2026)
> 분석일: 2026-08-06 · 분석 방식: 브라우저 블랙박스 분석(DOM·네트워크·매니페스트·UI 조작)

## 0. 선행 확인: 법적 경계

원작은 다음과 같이 **명시적으로 보호**되어 있다.

- `<meta name="copyright">` 및 스크립트 상단 주석: `Copyright © 2026 수달쌤. All Rights Reserved. 무단 복제·수정·배포를 금지합니다.`
- 스크립트 본문이 **base64 청크 → 런타임 eval 복호화** 형태로 난독화되어 있음 (의도적 코드 보호 조치)

따라서 이 계획은 **원작 코드·에셋·문구를 복제하지 않는 독자 구현**을 전제로 한다.

| 구분 | 판단 | 처리 |
|---|---|---|
| 장르·게임 규칙 (뱀서라이크 + 퀴즈 강화) | 아이디어 영역, 보호 대상 아님 | 자유롭게 채택 |
| 교육과정 단원 구성 (2022 개정) | 공개 국가 교육과정 | 자유롭게 채택 |
| **소스 코드** | 저작권 보호 + 난독화로 보호 의사 명시 | **역난독화·추출 금지**, 전량 신규 작성 |
| **문제 지문·해설·UI 문구** | 어문저작물 | 전량 신규 작성 |
| **캐릭터(수달 용사)·무기 네이밍·비주얼** | 저작권 보호 | 자체 IP로 교체 |
| 상표성 요소 (`수학 서바이버` 타이틀, @otter_ssam) | 출처 혼동 유발 | 사용 금지 |

**결론:** "동일한 재미 구조를 가진 우리 게임"은 만들 수 있고, "같은 게임을 베낀 것"은 만들 수 없다. 아래 계획은 전자를 목표로 한다.

### 1.3 게임 시스템

**코어 루프** — 이동만 조작, 공격은 자동, **10분 생존**이 목표.

| 시스템 | 내용 |
|---|---|
| 학년 선택 | 3~6학년 (2022 개정 1학기), 학년별 단원 태그 노출 |
| 신원 입력 | 용사 이름 + **학급 코드** (학급 단위 랭킹 대결용) |
| 주무기 선택 | 4종 — 무기에 따라 **캐릭터 스킨 변화**, 각 무기에 "밸런스형/광역 관통형" 등 타입 라벨 + 각성 짝꿍 힌트 표시 |
| 성장 | 몬스터 처치 → 보석 드랍 → XP → 레벨업 |
| **레벨업 퀴즈** | 레벨업 시 문제 출제 → **정답 시 강화 카드 3택**, 오답 시 재도전 가능(정답률만 기록) |
| **각성(진화)** | 무기 Lv.5 + 짝꿍 보조 아이템 보유 → 레벨업 문제 정답 시 진화. **총 10종 조합** |

| 회복 | 🐟생선 도둑 고양이 처치 → 생선 드랍 → HP +50 |

| 일시정지 | ESC/버튼 — 진행 통계 + 보유 액티브/패시브 스킬 목록 열람 |

### 1.4 원작 설계에서 배울 점 / 바꿀 점

**계승할 것**
- **에셋 제로 전략** — 이모지 + 캔버스 절차 드로잉으로 로딩 즉시, 용량 최소. 학교 와이파이 환경에서 결정적 이점
- **단일 파일 배포** — 오프라인 PWA와 궁합이 좋음
- **퀴즈를 보상 게이트로** — 문제 풀이가 "숙제"가 아니라 "강화 획득 수단"이 되는 배치
- **오답 페널티 없음** — 재도전 허용, 정답률만 기록 → 학습 이탈 방지
- **보스전 타이머 정지** — 문제 푸는 동안 불이익이 없어야 함
- **학급 코드** — 계정·로그인 없이 소셜 경쟁 확보 (개인정보 최소 수집)

**바꿀 것**
- 213KB 난독화 단일 스크립트 → **TypeScript 모듈 + 빌드 파이프라인** (테스트·밸런싱 반복 가능하게)
- 문제 데이터가 코드에 내장된 구조 추정 → **문제은행을 JSON으로 분리** (교사가 CSV로 편집 → 빌드 반영)
- 클라이언트 점수 그대로 전송 추정 → **서버 검증(Edge Function)** 추가

## 2. 클론 기술 설계

### 2.1 스택 선정

| 레이어 | 선택 | 사유 |
|---|---|---|
| 언어 | **TypeScript** | 엔티티·강화 효과 조합이 많아 타입 안전성 이득이 큼 |
| 빌드 | **Vite** | 개발 HMR, `vite-plugin-singlefile`로 단일 HTML 산출 가능 |
| 렌더링 | **Canvas 2D** (WebGL 미사용) | 적 200~400체 규모는 2D로 충분. 오브젝트 풀 + 오프스크린 프리렌더로 대응 |
| UI 오버레이 | **순수 DOM + 템플릿** (React 미사용) | 오버레이 9종·정적 구조. React는 게임 루프와 렌더 주기가 충돌하고 번들만 키움 |
| 상태 | 단일 `GameState` 객체 + 시스템 함수 | ECS는 이 규모에 과설계 |
| PWA | `vite-plugin-pwa` (Workbox) | 오프라인 캐싱·설치 프롬프트 |
| 백엔드 | **Supabase**(Postgres + RLS) + **Cloudflare Worker**(점수 검증) | 랭킹 저장은 Supabase, 부정 점수 검증은 배포와 같은 Worker에 두어 플랫폼을 늘리지 않는다 |
| 배포 | **Cloudflare Workers Static Assets** (확정) | `wrangler.jsonc`로 설정을 저장소에 둔다(`assets.directory=./dist`). 빌드 `npm run build`, 배포 `npm run deploy`(`wrangler deploy`). Pages 대신 Workers를 고른 이유: 이후 **점수 검증 API를 같은 Worker에 얹을 수 있어** Supabase Edge Function이라는 두 번째 플랫폼을 늘리지 않아도 된다 |
| 테스트 | Vitest (로직) + Playwright (E2E 스모크) | 밸런스 로직 회귀 방지 |

> **React를 쓰지 않는 이유**: 60fps 캔버스 루프가 렌더의 주체이고 DOM UI는 상태 전이 시점에만 갱신된다. React를 넣으면 두 개의 렌더 주기를 동기화해야 하고 얻는 게 없다. 팀이 React에 크게 익숙하다면 **오버레이 레이어에만** 도입하고 게임 루프는 분리할 것.

### 2.3 데이터 모델

**문제 — 기존 자산 재사용 (`~/WorkSpace/low-grade-operator-exercise-web`)**

문제를 신규 집필하지 않고 **사내 기존 프로젝트의 문제 생성기를 그대로 가져다 쓴다.**

*재사용 대상 실측*

| 항목 | 내용 |
|---|---|
| 파일 | `public/problems.js` (744줄, 의존성 없는 IIFE) |
| 공개 API | `window.Curriculum = { GROUPS, findGroup, findItem, generateSet, itemMeta }` |
| 커버리지 | **8개 학기군(3-1 ~ 6-2) · 75개 문제 유형** — 원작(1학기만)보다 넓음 |
| 방식 | 정적 문제은행이 아닌 **생성기(`gen()`)** → 사실상 무한 출제, 중복 회피 로직 내장(`generateSet(itemId, count, exclude)`) |
| 성취기준 | `STD` 맵으로 2022 개정 코드(`4수01-04` 등) 매핑 완료 |
| 문제 모델 | `{ promptHtml, blanks[] }` — 빈칸 `<span class="blank" data-bi="N">`, 정답은 문자열 배열 |
| 렌더 자산 | `public/styles.css`의 `.expr .frac .mixed .vexpr .blank` 등 수식·세로셈 스타일 재사용 가능 |

*학기군별 유형 수*: 3-1 15 / 3-2 13 / 4-1 6 / 4-2 9 / 5-1 9 / 5-2 3 / 6-1 7 / 6-2 13

**어댑터가 필요하다 — 이것이 유일한 신규 작업**

원 프로젝트는 **주관식 빈칸 입력**, 게임은 **4지선다**다. 어댑터 `quiz/adapter.ts`가 변환한다.

**구현 완료** — `src/quiz/adapter.ts` · `src/quiz/distractors.ts` (PoC 검증 완료)

답란 구조를 DOM으로 판별해 5가지 정답 형태를 모두 지원한다. (초안의 "단일 빈칸만 채택" 제한은 불필요해서 폐기)

| 형태 | 답란 구조 | 보기 표기 |
|---|---|---|
| `int` / `decimal` | 빈칸 1개 | `822` / `3.4` |
| `fraction` | `.frac` 안 분자·분모 빈칸 | 세로 분수 |
| `mixed` | `.mixed` 안 정수+분자+분모 | 대분수 |
| `fracPair` | 분수 2개(빈칸 4개) — 통분 | `3/12, 8/12` |
| `quotRem` | 빈칸 2개 + `…` | `7…3` |

> 주의: 좌변 피연산자도 `.frac`/`.mixed`로 렌더되므로 **빈칸을 품은 노드만** 답란으로 인정해야 한다. 이걸 놓쳐 대분수 3개 유형이 전량 변환 실패했다(PoC에서 발견·수정).

*오답(distractor) 생성 규칙* — 초등 오답 패턴을 모사해야 "찍어서 맞히기"를 막는다.

| 정답 형태 | 오답 생성 |
|---|---|
| 자연수 | 자릿수 실수(×10, ÷10), 받아올림 누락(±10, ±100), 근접값(±1, ±2) |
| 곱셈 결과 | 부분곱 누락형(`a×b`의 십의 자리 곱 빠뜨린 값) |
| 나눗셈 몫 | 몫±1, 나머지를 몫으로 오인한 값 |
| 분수 | 분모·분자 뒤바뿜, 약분 누락형, 분모끼리 더한 오답 |
| 소수 | 소수점 위치 오류(×10, ÷10), 자릿수 정렬 실수 |

- 생성 후 **중복 제거 + 음수/비현실 값 필터 + 정답과의 거리 검증**
- 정답 인덱스 분포를 25%씩 균등하게 셔플 (원작도 정답 위치가 고정되어 있지 않음)

**PoC 실측 결과** (75개 유형 × 40문항 = 3,000문항)

| 지표 | 목표 | 초기 | 수정 후 |
|---|---|---|---|
| 변환 성공 | 전 유형 | 66% (4개 유형 0%) | **100% (전 유형 40/40)** |
| 정답 위치 분포 | 각 25% | 24.4/25.8/25.7/24.1 | **25.8/23.6/25.0/25.7** |
| 정답이 최댓값 | 25% | **3.4%** ← 편법 성립 | **22.6%** |
| 정답이 최솟값 | 25% | 19.2% | **22.8%** |
| 보기 중복 | 0 | 0 | **0** |

PoC가 잡아낸 결함 3건:

1. **대분수 3개 유형 전량 변환 실패** — 좌변 피연산자도 `.mixed`라 답란으로 오탐
2. **통분(빈칸 4개) 미지원** — `fracPair` 형태 추가로 해결
3. **정답이 최댓값인 비율 3.4%** — `×10` 오답이 항상 최댓값이 되어 *"제일 큰 보기는 정답이 아니다"* 가 성립했다. 오답 후보를 위아래 **대칭**으로 확보하고, 정답의 크기 순위를 먼저 무작위로 정한 뒤 그 순위가 되도록 오답을 고르는 방식으로 수정

> 3번이 이 PoC의 존재 이유다. 눈으로 문항만 봤다면 "그럴듯한 오답"으로 보여 그냥 넘어갔을 결함이다.

**남은 과제**: 일부 유형(나머지가 있는 소수의 나눗셈 등)은 여전히 최댓값 비율이 10% 미만 — 해당 형태의 후보 대칭성 보완 필요.

**커버리지 공백 — 보완 필요**

재사용 프로젝트는 **연산 연습 전용**이라 다음 영역이 없다. 블랙박스 측정에서 원작은 이 영역도 출제했다.

| 영역 | 원작 출제 확인 | 재사용 프로젝트 | 대응 |
|---|---|---|---|
| 사칙연산·분수·소수 | ○ | **○ (전부 커버)** | 그대로 사용 |
| 규칙 찾기(등차수열) | ○ | ✕ | 생성기 신규 추가(간단) |
| 도형의 이동(밀기·뒤집기·돌리기) | ○ | ✕ | 개념형 — 소량 정적 문항으로 보완 |
| 자료와 그래프(막대그래프) | ○ | ✕ | 생성기 신규 추가 |
| 각도·부피·비율 | – | △ (비율·부피 단위만) | 부분 보완 |

→ **연산 영역은 0일, 보완 영역만 2~3일** 규모. 기존 480문항 집필 대비 절감 효과가 결정적이다.

**세이브 / 랭킹**

**세이브 / 랭킹**
```ts
type SaveState = { grade, name, classCode, bestByGrade: Record<grade, number>, session?: SerializedRun };
type ScoreRow  = { id, name, class_code, grade, score, survive_ms, kills, level, accuracy, created_at };
```

**Supabase 스키마**
```sql
create table scores (
  id uuid primary key default gen_random_uuid(),
  name text not null check (char_length(name) between 1 and 12),
  class_code text check (char_length(class_code) <= 12),
  grade smallint not null check (grade between 3 and 6),
  score int not null check (score >= 0),
  survive_ms int not null, kills int not null,
  level smallint not null, accuracy smallint not null,
  created_at timestamptz default now()
);
create index on scores (class_code, grade, score desc);
create index on scores (grade, score desc);
alter table scores enable row level security;
create policy "read all" on scores for select using (true);
-- INSERT는 정책으로 막고 Edge Function(service role)만 허용
```

**부정 점수 방지** (학급 랭킹이 있으면 반드시 시도가 나온다)
1. 클라이언트는 점수와 함께 **런 요약**(시드, 생존시간, 레벨, 처치수, 정답 로그 해시) 전송
2. Edge Function이 **물리적 상한 검증** — 생존시간 대비 최대 가능 처치수/레벨/점수 범위를 초과하면 거부
3. 동일 IP·이름의 초당 제출 **레이트 리밋**
4. 완벽 방어는 불가능 → **교사용 신고/삭제 기능** 제공이 현실적 안전판

**제외 2건**

| 제외 항목 | 사유 |
|---|---|
| ~~모범생 (특수, 모든 능력치 +5%)~~ | 일반 패시브 **황금별**과 효과가 동일. 황금별에 `+5%` 수치를 흡수시키고 특수 목록에서 제외. 특수 패시브는 "규칙을 바꾸는 것"만 남긴다 |
| ~~스피드 (쿨타임 감소)~~ | **암산력(공격속도 증가)**과 동일 축. 서바이버형에는 별도 액티브 스킬이 없어 쿨타임과 공격속도가 같은 값이다. 암산력으로 통합 |

**유지하되 차별화 필요 4쌍** — 설명만 보면 겹치지만 기계적으로 분리 가능해서 남겼다. Phase 0에서 확정할 것.

| 쌍 | 차별화 방향 |
|---|---|
| 자 ↔ 그래프빔 | 자 = **근거리 고정 길이** 직선, 그래프빔 = **화면 끝까지 관통**하는 장거리 광선 |
| 연필 ↔ 로켓연필 | 연필 = 자동조준 후 **직진**, 로켓연필 = **유도 곡선 추적** |
| 노트 ↔ 시험지 | 노트 = **전방 부채꼴 다단 히트**, 시험지 = **전방위 산개** |
| 행운 ↔ 행운의 네잎클로버 | 행운 = 상자 **출현 확률**, 네잎클로버 = 상자 **등급**. 같은 축에 두 스탯이 붙으므로 곱연산 폭주 주의 |

**사양 보완 필요 3건**

1. **숫자큐브 "벽을 튕기며 이동"** — 무한 스크롤 맵에는 벽이 없다. 위 표에서는 *화면 경계 반사*로 재정의했다. 다른 의도였다면 알려줄 것
2. **각성 없는 무기 15종** — 25종 중 10종만 진화 경로가 있다. 각성이 핵심 보상인데 무기의 60%가 막다른 길이면 선택 동기가 무너진다. 진화 조합을 추가하거나, 각성 가능 무기를 "주무기"로 분리하는 설계 필요
3. **진화에 쓰이지 않는 패시브 4종** (창의력·마법가방·끈기·황금별) — 순수 스탯 패시브로 남길지, 진화 재료로 편입할지 결정 필요

### 2.5.6 규모 영향 — 단계별 투입 필요

무기 25 + 패시브 14 + 특수 9 + 각성 10 = **58개 콘텐츠**다. 원작(무기 10·패시브 6)의 3배가 넘고, 무기 1종은 곧 **발사 패턴 1개 + 밸런스 곡선 1개 + 테스트 1세트**를 뜻한다. Phase 2를 1.5주로 잡은 산정은 이 규모를 담지 못한다.

| 단계 | 무기 | 패시브 | 특수 | 각성 | 목적 |
|---|---|---|---|---|---|
| **파일럿** | 6 | 5 | 1 | 3 | 재미 구조 검증. 연필·샤프펜슬·컴퍼스·각도기·계산기·지우개 |
| **정식 1차** | 12 | 10 | 4 | 6 | 빌드 분기가 성립하는 최소 폭 |
| **확장** | 25 | 14 | 9 | 10+ | 전체 사양. 각성 없는 무기 보완 이후 |

> 파일럿 6종은 **각성 짝꿍이 있는 무기 위주**로 골랐다. 각성을 못 보면 이 게임의 핵심 보상을 검증하지 못한다.

## 2.6 모바일 · 태블릿 동등 경험 (필수 요건)

실사용 환경이 교실 태블릿이므로 **데스크톱과 모바일/태블릿의 조작·UI 경험이 동일**해야 한다. "돌아가긴 한다" 수준은 미달로 본다.

### 조작 — 단일 입력 추상화

세 가지 입력을 **하나의 정규화 벡터 `{x, y}` (‖v‖ ≤ 1)** 로 합류시키고, 게임 로직은 그 벡터만 본다.

| 입력 | 처리 |
|---|---|
| 키보드 | 방향키 / WASD. 대각선은 정규화해 속도 이득 제거 |
| 터치 | **플로팅 조이스틱** — 화면 아무 곳이나 누른 지점이 원점이 되고 드래그 방향·거리가 벡터. 고정 위치 스틱은 손 위치를 강제해 작은 화면에서 불리하다 |
| 마우스 | 터치와 **동일한 플로팅 조이스틱**을 Pointer Events로 공유. 데스크톱에서도 같은 조작감이 나오고 코드도 하나로 유지된다 |

- Pointer Events 단일 경로(`pointerdown/move/up`)로 구현 — 터치·마우스·펜을 분기 없이 처리
- 데드존 8% / 최대 반경 64px / 원점은 화면 밖으로 나가지 않도록 클램프
- `setPointerCapture`로 드래그 중 이탈 방지, `touch-action: none`으로 스크롤·확대 차단

### 화면 — 안전 영역과 밀도

| 항목 | 기준 |
|---|---|
| 뷰포트 | `viewport-fit=cover`, `user-scalable=no`, `overscroll-behavior: none`, `body { position: fixed }`로 바운스 스크롤 차단 |
| 노치/홈 인디케이터 | HUD·오버레이 버튼은 `env(safe-area-inset-*)` 패딩 안쪽에만 배치 |
| 캔버스 해상도 | CSS 픽셀 × `min(devicePixelRatio, 2)`. 태블릿에서 DPR 3을 그대로 쓰면 픽셀 수가 2.25배로 늘어 프레임이 무너진다 |
| 회전 | 세로/가로 모두 지원. 리사이즈 시 카메라 시야(월드 단위)를 유지해 **가로 화면이 유리해지지 않도록** 보정 |
| 터치 타깃 | 모든 버튼·보기 선택지 **최소 44×44px**, 인접 간격 8px 이상 |
| 퀴즈 보기 | 좁은 화면에서 2×2 그리드 → 1열로 전환. 손가락으로 가려지지 않도록 지문은 상단 고정 |

### 성능 — 저사양 태블릿 기준

- 기준 기기는 데스크톱이 아니라 **교실 보급형 안드로이드 태블릿**으로 잡는다
- 프레임이 45fps 아래로 3초 이상 지속되면 **자동 저사양 모드**(파티클 감소, 적 렌더 간소화, 그림자 제거)
- `visibilitychange`에 일시정지 — 백그라운드에서 타이머가 흐르면 태블릿 멀티태스킹 시 억울한 사망이 발생한다

### 검증 방법

- Vite dev 서버를 `host: true`로 열어 **같은 네트워크의 실기기에서 직접 확인** (에뮬레이터만으로 판단하지 않는다)
- Phase 7 체크리스트에 실기기 4종(보급형 안드로이드 태블릿 / 아이패드 / 안드로이드 폰 / 크롬북) 통과를 명시

## 3. 단계별 작업 계획

전체 예상 **약 8~10주(1인 기준)**. 각 단계는 독립적으로 플레이 가능한 상태로 끝난다.

### Phase 0 — 기획 확정 (3일)
- [ ] 자체 IP 확정: 캐릭터·세계관·무기 네이밍 전량 신규 (원작 명칭 미사용)
- [ ] 대상 학년·단원 범위 확정, 교사 검수자 섭외
- [ ] 밸런스 1차 설계표 작성 (아래 4장 참고)
- **산출물**: 기획서 1장 + 밸런스 스프레드시트
- **완료 기준**: 무기 10종·패시브 6종·각성 10조합의 이름과 효과가 표로 확정

### Phase 1 — 엔진 골격 (1주)
- [ ] Vite + TS 프로젝트, 고정 타임스텝 루프, 캔버스 리사이즈(DPR·safe-area 대응)
- [ ] 입력 통합 계층 (키보드 + 포인터 드래그 + 가상 스틱)
- [ ] 카메라, 오브젝트 풀, 균일 그리드 충돌
- [ ] 디버그 HUD (fps, 엔티티 수, 히트박스 표시)
- **완료 기준**: 캐릭터가 무한 맵을 돌아다니고 더미 적 300체가 60fps로 추적해 온다

### Phase 2 — 전투 코어 (1.5주)
- [ ] 자동 공격 프레임워크 (무기 = 쿨다운 + 발사 패턴 + 스케일링 함수)
- [ ] 주무기 4종 구현 (조준탄 / 관통 검기 / 포물선 투척 / 산탄)
- [ ] 적 3~4종 + 스폰 웨이브 스케줄러
- [ ] 피격·넉백·사망, 보석 드랍 → 자석 흡수 → XP → 레벨업 이벤트
- **완료 기준**: 퀴즈 없이 10분 생존 루프가 끝까지 돌아감

### Phase 3 — 퀴즈 · 성장 (1주 — 문제 재사용으로 0.5주 단축)
- [ ] `problems.js` 이식 (IIFE → ES 모듈로 래핑, 로직 수정 없음) + `styles.css`의 수식 스타일 발췌
- [ ] **4지선다 어댑터 + distractor 생성기** 구현 및 단위 테스트 (정답 위치 편향·중복 보기 검증)
- [ ] 공백 영역 생성기 보완 (규칙 찾기, 막대그래프, 도형 이동)
- [ ] 출제 정책 (학년→학기군 매핑, 유형 균등 분배, `exclude`로 미출제 우선)
- [ ] 레벨업 → 퀴즈 오버레이 → 정답 시 강화 카드 3택 → 적용
- [ ] 패시브 6종 + 스탯 모디파이어 파이프라인
- [ ] 각성 판정(무기 Lv.5 + 짝꿍) + 진화 무기 10종 + 각성 연출
- [ ] 정답률 집계·HUD 표시
- **완료 기준**: 문제를 풀며 빌드를 완성하는 한 판이 성립. **교사 1인 실사용 피드백 수령**

### Phase 4 — 타임라인 · 보스 (1주)
- [ ] 중간보스 2체(3분·6분) — **전투 중 타이머 정지**
- [ ] 8~9분 특별 문제 구간 + 초월(파워스파이크)
- [ ] 최종보스 — **문제 정답으로 방어막 해제**하는 페이즈 구조
- [ ] 보너스 몬스터(정답 시 맵 전체 자석/폭탄), 회복 아이템
- **완료 기준**: 10분 전체 페이싱이 기승전결을 갖춤

### Phase 5 — 메타 · UI (1주)
- [ ] 시작 화면, 학년 선택, 무기 선택(스킨 프리뷰), 게임 방법, 도감
- [ ] 일시정지(통계 + 보유 스킬), 결과 화면(별점·칭호·신기록)
- [ ] 이어하기(세션 직렬화), 학년별 최고 점수 로컬 저장
- **완료 기준**: 첫 방문자가 설명 없이 한 판을 끝낼 수 있음

### Phase 6 — 백엔드 · PWA (4일)
- [ ] Supabase 테이블·RLS·인덱스, Edge Function 점수 검증
- [ ] 명예의 전당 (전체 / 학급 코드 조회), 지연 로드
- [ ] PWA: manifest, service worker, 오프라인 플레이, 설치 프롬프트
- [ ] Cloudflare Workers 배포 확인 (`wrangler.jsonc` assets-only), `public/_headers`로 캐시 정책 지정
- [ ] 점수 검증 엔드포인트를 같은 Worker에 추가 (`main` 엔트리 도입 시점)
- **완료 기준**: 비행기 모드에서 플레이 가능, 온라인 복귀 시 점수 제출

### Phase 7 — 밸런싱 · QA (1.5주)
- [ ] 자동 플레이 시뮬레이터 (AI 조작으로 1000판 배치 → 클리어율·평균 레벨·무기별 승률 통계)
- [ ] 목표 지표로 수렴시키기 (4장 참고)
- [ ] 실기기 테스트 **4종 통과 필수**: 보급형 안드로이드 태블릿 / 아이패드 / 안드로이드 폰 / 크롬북 (2.6 기준)
- [ ] 접근성: 색맹 대비, 폰트 크기, 화면 흔들림 끄기 옵션, 저사양 모드
- [ ] **교실 파일럿 1회** (한 학급 실사용 관찰)
- **완료 기준**: 목표 지표 달성 + 파일럿 피드백 반영

### Phase 8 — 출시 (3일)
- [ ] 도메인·배포 파이프라인, 에러 로깅(Sentry 무료 티어)
- [ ] 개인정보 처리방침 (아동 대상 — 아래 5장)
- [ ] 교사용 안내 페이지 (학급 코드 사용법)

## 4. 밸런스 목표 지표

Phase 7의 수렴 목표. 수치는 시뮬레이터로 검증한다.

| 지표 | 목표값 | 이유 |
|---|---|---|
| 10분 클리어율 (해당 학년 평균 학생) | **35~50%** | 너무 쉬우면 성취감이 없고, 20% 미만이면 이탈 |
| 한 판 레벨업 횟수 | 15~20회 | = 문제 노출량. 10분에 20문항이 학습 밀도 상한 |
| 문제 1개당 소요 | 8~15초 | 20초를 넘으면 게임 리듬이 끊김 |
| 무기별 클리어율 편차 | ±10%p 이내 | 특정 무기 강제 선택 방지 |
| 각성 도달률 | 70% 이상 | 각성이 이 게임의 핵심 보상 — 대부분 경험해야 함 |
| 첫 사망 시점 (미숙련) | 4~6분 | 즉사도, 무사통과도 아닌 구간 |

**밸런싱 원칙**
- 모든 수치는 `balance.ts` 한 파일에 상수로 격리 — 코드 수정 없이 튜닝
- 난이도는 **적 체력·스폰 밀도**로 조절하고, **문제 난이도로는 조절하지 않는다** (학습 난이도와 게임 난이도의 분리)
- 오답에 게임적 페널티를 주지 않는다 (원작의 좋은 결정) — 틀린 학생이 더 불리해지면 학습 도구로서 실패
